# 版本发布与软件内更新

## 先理解这三个东西

- **版本号**：软件的编号，例如 `2.1.0`。唯一修改位置是项目根目录的 `version.py`。修复问题通常增加最后一位（`2.1.1`），增加功能增加中间一位（`2.2.0`）。新版本号必须更大。
- **Tag（标签）**：在代码仓库里给某一次提交做标记，例如 `v2.1.0`，表示用这一份代码构建 2.1.0。普通提交或推送不会发布；推送版本标签才会触发构建。
- **Release（发布）**：给用户看的下载页面，包含版本、更新说明和附件。软件检查的是公开发布仓库中的最新正式 Release，比较版本号；不会检查私有代码提交，也不会因为链接变化就执行文件。

每次仍然需要生成完整安装包，只是改由 GitHub Actions 的 Windows 机器完成。无需保持自己的电脑开机。

代码仓库：<https://github.com/TrevorZsl/z-note>（私有）。
下载仓库：<https://github.com/TrevorZsl/z-note-releases>（公开，仅用于安装包和公开说明）。

## 一次性配置

公开发布仓库已经创建并初始化，默认分支为 `main`，不要把私有项目代码推送进去。

跨仓库上传需要一把只允许写发布仓库的钥匙；GitHub 自动生成的 `GITHUB_TOKEN` 只适用于当前代码仓库，不能代替它。

1. 登录 GitHub，打开头像 → **Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token**。
2. Resource owner 选择 `TrevorZsl`，Repository access 选择 **Only select repositories**，只选 `z-note-releases`。
3. Repository permissions 中将 **Contents** 设为 **Read and write**，其他权限保持默认。选择合适的有效期，并记录到期时间。
4. 生成后复制令牌。打开私有代码仓库 → **Settings → Secrets and variables → Actions → New repository secret**。
5. Name 填 `RELEASE_TOKEN`，Secret 粘贴刚生成的令牌，保存。不要将令牌放进代码、更新说明或聊天。
6. 确认代码仓库的 **Actions** 已开启，并允许使用 GitHub 官方 Actions。工作流本身只申请源仓库的 `contents: read`；跨仓库令牌只在最后上传阶段注入。

令牌到期后，新建同样权限的令牌并替换这个 Secret。它到期只影响发布，不影响用户下载已有正式版本。

## 第一次发布 2.1.0

这一版已经包含自动构建流程，不需要先在本机手工打包。

1. 确认 `version.py` 为 `APP_VERSION = "2.1.0"`，检查 `releases/2.1.0.md` 的公开更新说明。
2. 将此次功能、工作流、测试和文档提交并推送到原来的私有代码仓库。不要把安装包提交到 Git。
3. 在对应提交上创建并推送标签：

   ```powershell
   git tag v2.1.0
   git push origin v2.1.0
   ```

4. 打开私有仓库的 **Actions → Build Windows release**。构建将校验版本、运行更新相关测试，生成 EXE 和 Inno Setup 安装包。
5. 成功后，在公开发布仓库的 **Releases** 中找到 **Draft**。附件应包含：

   - `z-note-setup-2.1.0.exe`：给用户安装或覆盖升级的完整安装包。
   - `SHA256SUMS`：客户端下载后验证安装包完整性所需的校验文件。

6. 下载草稿安装包，完成下面的验收。草稿只有有权限的维护者可见，普通用户此时检查不到它。
7. 检查公开更新说明，**不要勾选预发布版本（pre-release）**，发布并设为 **Latest release**。确认两个附件都上传完整再发布。

公开仓库也会产生同名标签，但它指向公开仓库自身，不包含私有代码。

已发出的两版不含更新功能：用户需要最后手动下载一次 2.1.0。先从托盘退出旧版，运行新安装包直接覆盖，不要卸载。之后在设置底部使用“检查更新”。

## 以后发布

例如发布 2.1.1：

1. 修改 `version.py` 中的版本号为 `2.1.1`。
2. 新建 `releases/2.1.1.md`，只写准备公开给用户的更新说明。不要放内部路径、令牌或私有信息。
3. 提交并推送代码，再运行 `git tag v2.1.1`、`git push origin v2.1.1`。
4. 等 Actions 成功，验证草稿安装包，再正式发布并设为 Latest。

不要修改已正式发布版本的附件，也不要移动已发布标签。发现问题应发更高版本，例如 `2.1.2`。

构建失败不会正式发布。若失败发生在上传过程中，可能留下未完整上传的草稿；检查并删除失败草稿及其公开仓库标签，再在 Actions 中重跑。不要删除或覆盖正式发布的版本。两个附件必须来自同一次构建，不能混用。

不要依赖发布旧版来回滚：客户端不自动降级。需要撤回问题版本时，可取消其 Latest 状态，再以更高版本号发布修复。

## 用户操作与数据安全

设置 → 关于与更新 → **检查更新 → 下载并安装 → 立即安装**。

检查和下载都在后台进行，便签可继续使用；取消或关闭设置会取消尚未安装的任务。网络读取有超时，取消后可能需要等当前读取结束。源码运行和便携 EXE 只提供版本查询与发布页面链接；应用内安装面向带卸载程序的安装版。

下载通过大小和 SHA-256 校验后才会出现“立即安装”。点击后会再次校验，完成正文、标题和位置同步，严格保存数据并备份，再启动安装程序并退出。保存、备份或启动失败时，应用保持运行。若输入法仍在组词，请先完成输入再安装。

安装程序保留界面，复用原安装目录；如果提示 z-note 仍在运行，请从托盘退出再继续，不要强制结束进程。安装结束后保留原有的“启动 z-note”选项。若取消安装，可直接重新启动原版本。

- 程序默认位置：`%LOCALAPPDATA%\Programs\z-note`。
- 全部用户数据：`%APPDATA%\z-note\notes.json`。
- 升级前备份：`%APPDATA%\z-note\update-backups\notes-before-update-时间戳.json`，不会随启动备份轮转删除，可自行归档旧备份。
- 下载暂存：当前用户临时目录内的 `z-note-update-*` 文件夹。失败或取消会清理；已启动的安装包会保留，安装结束后可清理该临时文件夹。

覆盖安装只替换程序，不删除便签、设置、已完成记录和回收站。未来若修改数据格式，仍需另外实现兼容迁移。

恢复升级备份：先从托盘退出程序，额外保留当前 `notes.json`，再将选定备份复制为 `notes.json`，然后启动软件。不要在软件运行时覆盖数据文件。

SHA-256 校验用于发现损坏或文件混用，信任基础仍是 GitHub HTTPS 和发布账号安全，并不等于 Windows 代码签名。客户端不携带 GitHub 令牌。GitHub 无法访问或 API 请求受限时会提示重试，不影响日常离线使用。

## 本地构建与验收

仍可单独构建便携 EXE：

```powershell
python -m pip install -r requirements.txt pyinstaller
powershell -ExecutionPolicy Bypass -File scripts/package.ps1
```

需要本地安装包时，先安装 Inno Setup 6，再运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package.ps1 -Installer
# 若编译器在其他位置：追加 -Iscc "D:\Tools\Inno Setup 6\ISCC.exe"
```

输出为 `dist/z-note.exe`、`dist/z-note-setup-版本号.exe` 和 `dist/SHA256SUMS`。应用显示和安装包版本均来自 `version.py`，不要直接手工编译安装脚本。

首次安装及每个新版本首次启动时，程序会新增一张简明使用指南便签，保留已有便签和历史记录。显示记录随用户数据保存，同一版本重启或删除指南后不会重复创建；发布新版时仍需更新 `version.py`。欢迎便签由程序创建，无需在安装包内附带或覆盖用户数据。

正式发布前至少验证：

- 在已有旧版和真实数据的测试电脑上覆盖安装，内容、标题、位置、设置、已完成记录和回收站保留，卸载列表没有多出同一应用的第二条记录。
- 检查全新安装和保留旧数据升级后均出现当前版本的使用指南；同一版本重启不重复创建，删除指南后也不重建。即使关闭“启动时显示便签”，新版指南仍应可见。
- 检查升级前备份可读取；取消安装后旧版仍可启动。
- 以独立测试发布仓库构建两个版本，验证设置内发现新版、下载、校验、保存、退出和覆盖安装的完整链路。测试时只修改测试副本中的发布仓库常量及工作流目标，不向正式发布仓库上传假版本。
- 检查更新界面的文字换行、滚动和缩放；断网、取消下载、重复点击均不会卡住编辑器。

自动化测试使用模拟网络、临时数据和模拟安装进程；它们不能替代上面的真实安装验收。
